# 发布流程改造需求

## 一、背景

当前分支 `main-OldTeaBag-B188` 上的 `.github/workflows/publish.yml` 存在四处限制：

1. 公开发布只在 `main-OldTeaBag-B<数字>` 分支且仓库为 `kaedelcb/better-genshin-impact` 时可用，其他分支、其他仓库无法直接发布。
2. 必须手动勾选「创建 GitHub Release 草稿」或在版本号前手写 `release:` 前缀，默认行为不是发布。
3. 创建的是草稿（draft），还需人工确认后才公开。
4. 所有构建任务全部完成后，才由末尾一个独立任务一次性上传全部附件；任一环节失败则本次运行的产物全部无法进入 Release。

## 二、目标

把发布流程改为「分支无关、默认发布、直接公开、边构建边追加」的模式，减少人工步骤，并让已完成的成品尽早可见。

## 三、实施蓝本

**以分支 `DF4.3-Patch` 的 `.github/workflows/publish.yml` 为蓝本改造。**

理由：该蓝本没有引入 `tools/release_actions.py` 及其配套测试，发布完全由 YAML 与 `softprops/action-gh-release` 实现，改造不涉及任何 Python 脚本。

两个分支的相关文件对比：

| 文件 | `DF4.3-Patch` | `main-OldTeaBag-B188` |
| --- | --- | --- |
| `.github/workflows/publish.yml` | 有（790 行，12 个 job） | 有（846 行，13 个 job） |
| `tools/release_actions.py` | 无 | 有 |
| `Test/ReleaseActions/test_release_actions.py` | 无 | 有 |
| `.github/workflows/release-artifacts-check.yml` | 无 | 有 |

蓝本选用 `softprops/action-gh-release`。该 action 的行为：同 `tag_name` 的 Release 已存在时，**更新已有 Release 并追加附件**，而不是报错重建。这一特性是 R4「先建空 Release，之后各任务自行追加」能够纯 YAML 实现的前提。

## 四、需求项

### R1 去除分支名限制

- 移除工作流对触发分支名称的限制，任意分支手动触发均可执行发布流程。
- 移除对仓库所有者的限制，当前仓库自身即可发布。
- 保留版本号格式校验（语义化版本），该项不属于分支限制。

蓝本现状：`validate` 任务只做版本号格式校验，无分支判断，**本项无需改动**。

**验收**：在非 `main-OldTeaBag-B*` 的分支上手动触发，发布流程正常执行，不因分支名被拒绝。

### R2 默认发布 Release

- 触发参数中的发布开关默认值为「发布」，无需额外勾选即可进入发布流程。
- 不再要求版本号携带 `release:` 前缀；直接填写版本号即表示发布。
- 若仍保留该前缀作为兼容写法，需能被自动识别并剥离。

蓝本改法：`create-release` 输入的 `default: false` 改为 `true`。

**验收**：只填写版本号、不做其他勾选时，运行结束后仓库中出现对应版本的 Release。

### R3 删除草稿限制，直接发布

- 创建的 Release 状态为公开，不经过草稿阶段。
- 移除「草稿」与「发布」互斥的校验与提示。
- 移除发布前从草稿切换为公开的二次确认步骤。

蓝本改法：`softprops/action-gh-release` 的 `draft: true` 改为 `draft: false`。

**验收**：Release 创建完成后立即可被未登录用户访问，不出现「需手动点击发布」的中间态。

### R4 先创建 Release，再逐步追加成品

发布顺序调整为：

1. 校验通过后**立即创建**对应版本的空 Release（公开状态）。
2. 后续每个构建任务完成后，**自行把本次产出的成品上传到该 Release**，不等待其他任务。
3. 各任务互不阻塞；某个任务失败不影响其他任务已上传的成品。

成品与来源任务对应关系：

| 成品 | 来源任务 | Actions 产物名 | 产物路径 |
| --- | --- | --- | --- |
| `BetterGI_v<版本>.7z` | `build_dist` | `BetterGI_7z` | `dist/BetterGI_*.7z` |
| `BetterGI.Install.<版本>.exe` | `build_installer` | `BetterGI_Install` | `dist/BetterGI.Install.*.exe` |
| `BetterGI_Setup_v<版本>.exe` | `build_setup` | `BetterGI_Setup` | `BetterGI_Setup*.exe` |

注意：蓝本原 `create_release` 的 `needs` 是 `[validate, build_dist, build_installer]`，**未包含 `build_setup`**，因此原流程的 Release 里从来没有 `BetterGI_Setup` 安装向导。拆开后正好补上这一项。

**验收**：
- Release 在第一个成品产出前即已存在（可观察到空附件的时间窗口）。
- 三个成品分别出现，单个任务完成即上传，不等待全部完成。
- 中途失败时，已上传的成品保留在 Release 中。

## 五、实施方案

### 5.1 输入参数调整

```yaml
      create-release:
        type: boolean
        description: '创建并发布 GitHub Release'
        required: true
        default: true        # 原为 false
```

版本号输入去掉 `release:` 前缀相关说明，直接填版本号。若需兼容旧写法，在 `validate` 中加一行剥离：

```bash
version="${version#release:}"
```

### 5.2 新建独立建 Release 任务

将蓝本原有的 `create_release` 改造为「只建壳、不传附件」，`needs` 只保留 `validate`，使其在构建开始前就执行：

```yaml
  create_release:
    needs: [validate]
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: softprops/action-gh-release@v1
        with:
          tag_name: ${{ needs.validate.outputs.version }}
          name: BetterGI v${{ needs.validate.outputs.version }}
          draft: false
          prerelease: ${{ contains(needs.validate.outputs.version, '-') }}
          fail_on_unmatched_files: false
```

`fail_on_unmatched_files: false` 是必须的——此时没有附件，设为 `true` 会直接失败。

`tag_name` 会创建对应的 Git 标签。若标签已存在，该 action 会复用而非报错。

### 5.3 三个构建任务各自追加

在 `build_dist`、`build_installer`、`build_setup` 三个任务末尾，各自在原有 `upload-artifact` 步骤之后增加一步：

```yaml
      - name: 📤 追加到 Release
        uses: softprops/action-gh-release@v1
        with:
          tag_name: ${{ needs.validate.outputs.version }}
          draft: false
          fail_on_unmatched_files: true
          files: |
            <本任务产物路径>
```

三处 `files` 分别填：

| 任务 | `files` |
| --- | --- |
| `build_dist` | `dist/BetterGI_v${{ needs.validate.outputs.version }}.7z` |
| `build_installer` | `dist/BetterGI.Install.${{ needs.validate.outputs.version }}.exe` |
| `build_setup` | `BetterGI_Setup_v${{ needs.validate.outputs.version }}.exe` |

`build_setup` 的产物在仓库根目录（`ren BetterGI_Setup.exe BetterGI_Setup_v<版本>.exe`），不在 `dist/` 下，路径需注意。

### 5.4 依赖关系变化

改造后各任务依赖关系：

```
validate
  └─ create_release（建空 Release）

build_web_map_editor ─┐
build_web_scripts_list ─┴─ build_dist ──┬─ build_installer
                                        └─ build_setup
```

`build_installer` 与 `build_setup` 均只依赖 `build_dist`，二者可并行，各自完成后立即上传自己的成品。

### 5.5 与既有任务的关系

- `mirrorchyan_uploading`、`cnb_uploading`、`cnb_trigger`、`upload_to_steambird` 四个任务保持原样，不受本次改造影响。
- 它们仍依赖 `build_dist` 与 `build_installer`，产物仍通过 Actions artifacts 传递，与 Release 流程互不干扰。

### 5.6 完整改动清单

| 位置 | 改动 |
| --- | --- |
| `on.workflow_dispatch.inputs.create-release` | `default: false` → `true`，描述改为「创建并发布」 |
| `jobs.create_release` | `needs` 改为 `[validate]`；删除 `download-artifact` 步骤；`draft` 改 `false`；`fail_on_unmatched_files` 改 `false`；删除 `files` |
| `jobs.build_dist` 末尾 | 新增一步上传 `dist/BetterGI_v<版本>.7z` |
| `jobs.build_installer` 末尾 | 新增一步上传 `dist/BetterGI.Install.<版本>.exe` |
| `jobs.build_setup` 末尾 | 新增一步上传 `BetterGI_Setup_v<版本>.exe` |

## 六、约束与边界

- 版本号格式校验保持不变。
- 已有同版本标签或 Release 时不覆盖、不续传，按原逻辑报错并保留现状。
- 发布仍使用运行期临时令牌，不引入个人长期凭据。
- 三个任务并发向同一 Release 追加附件，可能触发 GitHub API 限流或短暂冲突；实施时需实测一次，必要时在任务级加 `concurrency` 分组。

### 关于 CI 检查失败

`main-OldTeaBag-B188` 上的 `.github/workflows/release-artifacts-check.yml` 会在 `publish.yml` 变更时自动触发，其中用例断言 `jobs["publish_release"]` 必须存在、`needs` 为四个任务、`if` 含 `!inputs.create-release`。改造后这些断言必然失败。

**该检查失败可以无视，不删除相关文件，也不修改测试用例。**
