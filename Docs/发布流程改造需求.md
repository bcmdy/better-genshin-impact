# 发布流程改造需求

## 一、背景

当前 `.github/workflows/publish.yml` 的发布流程存在四处限制：

1. 公开发布只在 `main-OldTeaBag-B<数字>` 分支且仓库为 `kaedelcb/better-genshin-impact` 时可用，其他分支、其他仓库无法直接发布。
2. 必须手动勾选「创建 GitHub Release 草稿」或在版本号前手写 `release:` 前缀，默认行为不是发布。
3. 创建的是草稿（draft），还需人工确认后才公开。
4. 所有构建任务全部完成后，才由末尾一个独立任务一次性上传全部附件；任一环节失败则本次运行的产物全部无法进入 Release。

## 二、目标

把发布流程改为「分支无关、默认发布、直接公开、边构建边追加」的模式，减少人工步骤，并让已完成的成品尽早可见。

## 三、需求项

### R1 去除分支名限制

- 移除工作流对触发分支名称的限制，任意分支手动触发均可执行发布流程。
- 移除对仓库所有者的限制，当前仓库自身即可发布。
- 保留版本号格式校验（语义化版本），该项不属于分支限制。

**验收**：在非 `main-OldTeaBag-B*` 的分支上手动触发，发布流程正常执行，不因分支名被拒绝。

### R2 默认发布 Release

- 触发参数中的发布开关默认值为「发布」，无需额外勾选即可进入发布流程。
- 不再要求版本号携带 `release:` 前缀；直接填写版本号即表示发布。
- 若仍保留该前缀作为兼容写法，需能被自动识别并剥离。

**验收**：只填写版本号、不做其他勾选时，运行结束后仓库中出现对应版本的 Release。

### R3 删除草稿限制，直接发布

- 创建的 Release 状态为公开，不经过草稿阶段。
- 移除「草稿」与「发布」互斥的校验与提示。
- 移除发布前从草稿切换为公开的二次确认步骤。

**验收**：Release 创建完成后立即可被未登录用户访问，不出现「需手动点击发布」的中间态。

### R4 先创建 Release，再逐步追加成品

发布顺序调整为：

1. 校验通过后**立即创建**对应版本的空 Release（公开状态）。
2. 后续每个构建任务完成后，**自行把本次产出的成品上传到该 Release**，不等待其他任务。
3. 各任务互不阻塞；某个任务失败不影响其他任务已上传的成品。

需要追加的成品与来源任务对应关系：

| 成品 | 来源任务 |
| --- | --- |
| `BetterGI_v<版本>.7z` | 绿色版打包 |
| `BetterGI.Install.<版本>.exe` | 安装器构建 |
| `BetterGI_Setup_v<版本>.exe` | 安装向导构建 |

**验收**：
- Release 在第一个成品产出前即已存在（可观察到空附件的时间窗口）。
- 三个成品分别出现，单个任务完成即上传，不等待全部完成。
- 中途失败时，已上传的成品保留在 Release 中。

## 四、约束与边界

- 版本号格式校验、附件来源（必须取自本次运行的原始构建产物）、标签不被移动等既有安全约束保持不变。
- 已有同版本标签或 Release 时不覆盖、不续传，按原逻辑报错并保留现状。
- 发布仍使用运行期临时令牌，不引入个人长期凭据。
